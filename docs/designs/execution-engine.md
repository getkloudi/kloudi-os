## Vision

### 10x Check
The 10x version would be a fully autonomous procedure runtime with parallel execution,
event-driven architecture (EventEmitter/bus instead of callbacks), BullMQ workers for
isolation, execution replay/debugging, and a rich real-time UI showing graph traversal
with node-by-node streaming. Phase 1 is the correct foundation — but the 10x version
ships Phases 1-3 as a cohesive product.

## Accepted Scope (added to this plan)
- Zod validation schemas for POST /procedures/:id/run and new cancel endpoint
- Structured logger metrics at engine start, node start/complete/fail, execution complete/fail
- Overall execution timeout (configurable, default 10 min)
- POST /executions/:id/cancel endpoint with engine cancellation flag check between nodes
- Per-workspace concurrent execution limit (default 5, reject with 429 when exceeded)
- Execution retention policy (configurable max age, cleanup job or on-demand)

## Additional Plan Requirements (from CEO Review)

### Error Handling Fixes (add to spec)
1. LLM 429 rate limit: exponential backoff + retry (not just timeout/network)
2. LLM empty response: return `{ status: 'failed', output: 'Empty LLM response' }`
3. LLM refusal: return `{ status: 'failed', output: 'LLM refused to respond' }`
4. ToolCallExecutor: wrap `registry.execute()` in try/catch, return failed on throw
5. SubEntityExecutor: wrap `procedureService.getProcedure()` in try/catch, return failed on throw
6. ContextManager.countTokens(null): return 0 instead of crashing

### Security Fix
- All execution queries (GET /executions/:id, GET /executions) must filter by workspaceId to prevent IDOR

### Deployment Strategy
- Merge PRs 1-4 sequentially, deploy as single unit to avoid broken intermediate states

### New Execution Status
- Add `cancelled` as a valid status alongside pending/running/waiting_input/completed/failed
